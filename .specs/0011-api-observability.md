## 1. Escopo

### Dentro do escopo

- **Métricas (push OTLP, sem `/metrics`):** rota nas métricas HTTP existentes; contador de operações de auth (sucesso e falha, com o motivo); duração por operação de auth.
- **Traces:** um span por caso de uso de auth, filho do span HTTP, com atributos sem PII.
- **Logs:** manter o JSON do pino com `trace_id` e `span_id` (já presentes no Loki), registrar o resultado de cada operação de auth e criar o link do log para o trace no Grafana.
- **Dashboards Grafana provisionados:** ampliar `infra/grafana/dashboards/api.json` e criar `infra/grafana/dashboards/auth.json` (duração p50/p95/p99, requisições por rota e por status, taxa de erro 4xx/5xx, operações de auth, logs e traces).
- **Testes automatizados** dos spans, dos contadores e da ausência de PII.
- **Documentação:** `ARCHITECTURE.md` §4.4, `DEVELOPMENT.md` §7 e `QA.md`; ADR registrando a escolha por push OTLP.

### Fora do escopo

- Endpoint `GET /metrics` no formato Prometheus e raspagem pelo Collector (decisão do Owner: manter OTLP; ver §11).
- Promtail, driver de log do Docker ou qualquer segundo caminho de logs para o Loki.
- Alertas, SLOs, on-call e canais de notificação.
- Telemetria do browser (`apps/app`), RUM e tracing do banco (Supabase/Postgres).
- Mudar a retenção dos backends locais (Loki guarda 24 h) ou provisionar backends de produção.
- Métricas e spans de domínios que ainda não existem (conectores, experts, LLM).
- `GET /api/v1/auth/session` e `GET /api/v1/health` como operações de auth (continuam só nas métricas HTTP).

## 2. Contexto

O pipeline já funciona de ponta a ponta: `apps/api/src/observability/telemetry.ts` envia traces, métricas e logs por OTLP HTTP ao Collector, que encaminha para Tempo, Mimir e Loki (`ARCHITECTURE.md` §4.4). Verificado em 2026-11-10 contra a infra local:

- **Logs:** chegam ao Loki com `service_name="rondo-api"`, `trace_id`, `span_id` e `requestId` (a correlação por id já existe; falta o link no Grafana).
- **Métricas:** `http_server_request_duration_seconds_*` existe no Mimir, mas **sem label de rota** (só método, status e esquema). Por isso não dá para ver duração ou erro por endpoint.
- **Traces:** só spans automáticos (HTTP e chamadas de saída). Os fluxos de auth não aparecem como operações de negócio.
- **Dashboard:** `api.json` tem um painel (req/s) e um texto de uso.
- O `.env` local ainda tem `OTEL_SERVICE_NAME=analytics-personas-api`; o `.env.example` e os defaults do código já usam `rondo-api`.

**Operações de auth e endpoints** (`apps/api/src/modules/auth/interface/auth.controller.ts`), com o status de sucesso de cada uma:

| `operation`           | Endpoint                                | Sucesso  | Observação                                                           |
| --------------------- | --------------------------------------- | -------- | -------------------------------------------------------------------- |
| `sign_up`             | `POST /api/v1/auth/sign-up`             | 201      | Pode falhar com 409 `EMAIL_ALREADY_REGISTERED`.                      |
| `confirm_account`     | `POST /api/v1/auth/confirm-account`     | 200      | Token ruim: 400 `TOKEN_INVALID_OR_EXPIRED`.                          |
| `sign_in`             | `POST /api/v1/auth/sign-in`             | 200      | 401 `INVALID_CREDENTIALS` ou 403 `EMAIL_NOT_CONFIRMED`.              |
| `sign_out`            | `POST /api/v1/auth/sign-out`            | 204      | Rota fechada: sem sessão, o guard responde 401 antes do caso de uso. |
| `forgot_password`     | `POST /api/v1/auth/forgot-password`     | 202 `{}` | Responde igual com ou sem conta (anti-enumeração).                   |
| `reset_password`      | `POST /api/v1/auth/reset-password`      | 204      | Token ruim: 400 `TOKEN_INVALID_OR_EXPIRED`.                          |
| `resend_confirmation` | `POST /api/v1/auth/resend-confirmation` | 202 `{}` | Igual ao `forgot_password` (R16, Should).                            |

Validação (400), limite (429) e sessão (401) são aplicados por pipe e guards **antes** do controller; só o filtro global de exceções (`all-exceptions.filter.ts`) enxerga todas as falhas.

O problema é que, quando um sign-in falha ou fica lento, quem opera a API não tem como ver qual endpoint, qual motivo e qual trace. Esta spec fecha essa lacuna sem trocar o caminho de telemetria que já funciona.

**Decisões do Owner (2026-11-10):** métricas continuam por push OTLP; entrega primeiro como spec; `userId` não vira atributo de span.

## 5. Fluxos e estados

- **Caminho feliz:** `bun run infra:up` → `bun run dev` → a pessoa faz sign-up, confirma a conta, entra, sai, pede e conclui o reset → no Grafana (`http://localhost:3000`) vê "Rondo — API" e "Rondo — Auth" com séries, logs e traces; clica numa linha de log e chega ao trace.
- **Vazio:** sem tráfego, os painéis mostram "No data" e o painel de texto explica como gerar tráfego (`bun run dev` e usar o app). Dashboard sem dados não é erro.
- **Carregando:** métricas têm intervalo de exportação de 15 s; os painéis podem levar até ~1 minuto para refletir uma ação nova (documentado em `QA.md`).
- **Erro:** se o Collector ou um backend estiver fora, a API responde normalmente (R12) e os painéis mostram lacuna no período. Se um `reason` fora do conjunto fechado for produzido, o teste de R13 falha.
- **Sucesso parcial:** telemetria parcial (ex.: logs chegam e traces não) não bloqueia nada; cada sinal é independente. O roteiro de `QA.md` valida os três separadamente.
- **Cancelamento/retry:** o exportador já tem timeout (`OTEL_EXPORTER_OTLP_TIMEOUT`) e em lote; não há retry novo. Dado perdido durante uma queda do Collector não é recuperado (comportamento aceito, já existente).

## 7. O que fazer

1. Ler `telemetry.ts`, `logger.ts`, `bootstrap.ts` e o `auth.controller.ts`; mapear onde cada caso de uso é chamado e onde validação (400) e limite (429) respondem antes dele.
2. Fazer a rota chegar às métricas HTTP (R1), com o template da rota e `unmatched` para o resto; escolher o mecanismo no plano (`.plans/0011-api-observability-plan.md`).
3. Criar um módulo pequeno em `apps/api/src/observability/` com o tracer, o contador, o histograma e a lista fechada de `reason` (R2, R3, R5, R15); o caso de uso chama esse módulo, não o SDK direto.
4. Instrumentar os seis casos de uso de auth (e `resend_confirmation`, R16), respeitando R4 e R6; cobrir validação e limite na contagem (R3).
5. Registrar o log `auth_operation` (R7) com o logger existente (`StructuredLogger`/`baseLogger`).
6. Provisionar o _derived field_ no Loki (R8) e, se couber, o _trace to logs_ no Tempo (R18).
7. Ampliar `api.json` (R9) e criar `auth.json` (R10), referenciando os datasources por `uid` (R11).
8. Escrever os testes com exportadores em memória e o teste de JSON dos dashboards (R13).
9. Atualizar `ARCHITECTURE.md` §4.4, `DEVELOPMENT.md` §7 e `QA.md`; registrar o ADR 0010 (R14).
10. Rodar os gates (`lint`, `check-types`, `build`, `test`, `test:integration`, `test:e2e`) e o roteiro manual no Grafana; ajustar o `OTEL_SERVICE_NAME` do `.env` local (§10).

## 8. O que não fazer

- Não criar `GET /metrics`, Promtail ou um segundo caminho de telemetria.
- Não usar e-mail, nome, `userId`, `sid`, token, link, IP, path cru ou query string como label, atributo ou campo de log.
- Não gravar mensagem de exceção ou stack em atributo de span; só o código de erro.
- Não diferenciar e-mail existente de inexistente em nenhuma métrica, span ou log (R4).
- Não criar label de cardinalidade aberta (qualquer valor vindo do cliente).
- Não chamar o SDK do OpenTelemetry direto nos casos de uso; usar o módulo de observabilidade.
- Não importar código de `apps/app` nem alterar o contrato HTTP dos endpoints de auth.
- Não alterar `turbo.json` nem o bloco gerenciado do `AGENTS.md`.

## 10. Resultado

Como validar que a spec foi atendida:

- **Comando/verificação:** `bun run infra:up`, `bun run dev`, executar o fluxo completo de auth pelo app e abrir `http://localhost:3000` (`admin`/`admin`, só local). Rodar `bun run lint`, `bun run check-types`, `bun run build`, `bun run test`, `bun run test:integration` e `bun run test:e2e`. Antes do roteiro, ajustar a linha `OTEL_SERVICE_NAME` do `.env` local para `rondo-api` (o `.env` não é versionado) e reiniciar a API.
- **Evidência esperada:** gates verdes; no Grafana, "Rondo — API" e "Rondo — Auth" com dados, consulta do `auth_operations_total` por `operation`, `outcome` e `reason`, um trace `auth.sign_in` com a falha marcada, e o clique de um log para o trace. Com o Collector parado, sign-up e sign-in ainda respondem 201 e 200.
- **Comportamento observável:** ver, por rota, por status e por motivo de auth, o que a API está fazendo, e navegar de um log ao trace dele; nenhum dado pessoal em nenhum dos três sinais.
